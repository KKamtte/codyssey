[[b1-2]]에서 배운 것. 과제 목표 "useEffect가 언제 실행되고 데이터 요청과 어떤 관계인가", "비동기 흐름의 상태를 UI로 어떻게 표현했나". B1-1의 fetch 버전은 [[fetch-async-ui-state]]. 문답은 [[b1-2-review-qa]] Q3·Q4·Q6.

## useEffect가 실행되는 때
- **처음 화면에 나타날 때(마운트) 한 번 + 의존성 배열의 값이 바뀔 때마다.** (문답에서 "처음 마운트"를 빠뜨림)
- `useCard(id)`는 `[id, reloadCount]`에 의존한다.
  - `/cards/1` → `/cards/2`로 가면 React Router가 **같은 `CardDetailPage`를 재사용**하고 `id`만 바꾼다. 재마운트가 아니므로 `id`가 의존성에 없으면 다시 불러오지 않아, 주소는 2번인데 1번 카드가 남는다.
  - "다시 시도"는 `reloadCount`를 1 올려 effect를 다시 실행시킨다.

## 정리 함수와 `ignore`: 늦게 온 응답 버리기
```js
useEffect(() => {
  let ignore = false
  fetchCard(id).then((card) => { if (!ignore) setState(...) })
  return () => { ignore = true }   // 다시 실행되기 직전·사라질 때 실행
}, [id, reloadCount])
```
- 1번 요청이 느리고 그 사이 2번으로 이동하면, 늦게 온 1번 응답이 2번 화면을 덮어쓸 수 있다.
- effect 실행마다 **자기 `ignore`**가 생기고(클로저), 다음 실행 직전 정리 함수가 **이전 실행의** `ignore`만 `true`로 만든다. 1번 응답은 버려지고 2번은 반영된다.

## 상태를 나눈 기준: "다시 해 보면 달라질까"
| status | 상황 | 화면 |
|---|---|---|
| `loading` | 아직 모름 | 스피너 |
| `success` | 받음 | 카드 |
| `notFound` | 서버가 "없다"고 확정 (`/cards/999`) | "찾을 수 없습니다" + 목록으로. 다시 해도 같으니 재시도 없음 |
| `error` | 요청 실패 (네트워크 등), 결과를 모름 | 에러 문구 + **다시 시도** |

## 빈 상태도 "왜 비었나"로 나눈다
| 경우 | 조건 | 안내 |
|---|---|---|
| 데이터가 없음 | `cards.length === 0` | "아직 카드가 없습니다" + **첫 카드 만들기** |
| 조건 때문에 안 보임 | `cards`는 있고 `visibleCards`가 0 | "조건에 맞는 카드가 없습니다" + **필터 초기화** |

(문답에서 두 번째 경우에 "첫 카드 만들기"라고 답함. 카드는 있으니 조건을 풀어 주는 게 맞다)

## "아직 모름"을 상태로 따로 둔다
- 보호 라우트도 같다. 새로고침 직후엔 Supabase가 저장된 세션을 확인하는 동안 `user`가 `null`이다. 그 순간을 "로그인 안 함"으로 판단하면 로그인한 사람도 `/login`으로 튕긴다. 그래서 `status === 'loading'`이면 기다린다. 자세히는 [[spa-routing-deploy]].
