# Mini NPU MAC Simulator

MAC(Multiply-Accumulate) 연산으로 N×N 패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 프로그램.

숫자표 두 개를 겹쳐 같은 자리끼리 곱하고 전부 더한다. 점수가 높은 쪽이 더 닮은 것이다.
AI 가속기(NPU)가 실제로 수행하는 연산의 원리를 외부 라이브러리 없이 반복문으로 직접 구현했다.

---

## 1. 실행 방법

```bash
python main.py
```

Python 3.8 이상이면 동작한다. 설치할 패키지는 없다(표준 라이브러리만 사용).

실행하면 메뉴가 나온다.

```

[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
3. 최적화 비교 (보너스)

선택:
```

| 선택 | 하는 일 |
|---|---|
| `1` | 3×3 필터 두 개(A, B)와 패턴을 직접 입력해 판정 |
| `2` | `data.json`의 5×5·13×13·25×25 케이스를 일괄 판정 |
| `3` | 2차원 접근과 1차원 접근의 성능 비교 (보너스 과제) |

모드가 끝나면 메뉴로 돌아온다. 잘못된 값을 넣어도 프로그램이 끝나지 않고 다시 묻는다.

## 2. 구현 요약

### 2.1 MAC 연산

이 과제의 핵심이다. 벡터화 라이브러리 없이 이중 반복문으로 구현했고,
**곱셈(Multiply)과 누적 덧셈(Accumulate)을 별도 문장으로 분리**해 두 단계가 코드에 그대로 드러나게 했다.

```python
def mac(pattern: Matrix, filter_matrix: Matrix) -> float:
    total = 0.0
    n = len(pattern)
    for row in range(n):
        for col in range(n):
            product = pattern[row][col] * filter_matrix[row][col]  # Multiply
            total = total + product                                # Accumulate
    return total
```

누적 시작값이 `0.0`이라 정수 행렬을 넣어도 반환은 항상 float다.
크기 검증은 이 함수가 하지 않는다. 호출 전에 끝내는 것을 전제로 두어, 시간 측정 구간을 순수 연산만으로 유지한다.

### 2.2 라벨 정규화

`data.json`은 같은 개념을 두 가지 표기로 적는다. `expected`는 `'+'`/`'x'`, 필터 키는 `'cross'`/`'x'`다.
내부에서는 **`Cross`, `X` 두 가지 표준 라벨만** 쓰고, 변환은 데이터가 들어오는 경계에서 끝낸다.

| 출처 | 원본 | 표준 라벨 |
|---|---|---|
| `expected` | `+` | `Cross` |
| `expected` | `x` | `X` |
| 필터 키 | `cross` | `Cross` |
| 필터 키 | `x` | `X` |

대응표를 **두 개로 분리**한 것이 핵심이다. `'x'`는 양쪽 공통이지만 `'+'`는 `expected` 전용,
`'cross'`는 필터 키 전용이다. 하나로 합치면 `expected: "cross"` 같은 잘못된 데이터가 조용히 통과한다.

정규화에 실패하면 예외를 던지지 않고 `None`을 반환한다. 예외를 던지면 모드 2 전체가 중단되기 때문이다.

### 2.3 동점 처리 정책 (epsilon)

부동소수점 연산은 `0.1`을 9번 더하는 것만으로도 오차가 생긴다.

```python
0.1 * 9 = 0.8999999999999999    # 0.9가 아니다
```

두 점수를 `==`나 부등호로 그냥 비교하면 이 1e-16 수준의 오차가 승부를 가른다.
그래서 **차이가 `EPSILON`(1e-9)보다 작으면 동점으로 보고 `UNDECIDED`로 판정**한다.

```python
def compare_scores(score_first, score_second, label_first, label_second):
    if is_tie(score_first, score_second):   # 동점 검사가 반드시 먼저
        return LABEL_UNDECIDED
    if score_first > score_second:
        return label_first
    return label_second
```

**동점 검사를 부등호보다 먼저** 한다. 순서를 바꾸면 허용오차 정책이 무력해진다.
그리고 `UNDECIDED`는 `expected`가 무엇이든 **FAIL**이다. 판정을 못 한 것이므로 정답과 일치할 수 없다.

## 3. 주요 메서드 설명

전체 41개 함수 중 핵심만 추린다.

### 3.1 연산과 판정

| 함수 | 설명 |
|---|---|
| `mac(pattern, filter_matrix) -> float` | 위치별 곱셈 → 누적 덧셈. 이 프로그램의 심장 |
| `is_tie(a, b) -> bool` | `abs(a - b) < EPSILON`. 점수 비교는 **전부 이 함수를 거친다** |
| `compare_scores(s1, s2, label1, label2) -> str` | 높은 쪽 라벨을 반환. 동점이면 `UNDECIDED` |
| `decide(score_cross, score_x) -> str` | 모드 2용. `compare_scores`에 `Cross`/`X`를 넘기는 껍데기 |
| `is_correct(predicted, expected) -> bool` | PASS/FAIL 판정. `UNDECIDED`와 `expected=None`은 무조건 False |

`compare_scores`가 라벨을 인자로 받는 이유가 있다. **모드 1의 판정 결과는 `A`/`B`이지 `Cross`/`X`가 아니다.**
사용자가 아무 필터나 넣을 수 있어 그것이 십자가라는 보장이 없기 때문이다.
비교 규칙은 양쪽이 같으므로 한 곳에만 적고 부르는 쪽이 이름만 정한다. 규칙이 흩어지면 epsilon 정책이 샌다.

### 3.2 입력 검증

| 함수 | 설명 |
|---|---|
| `parse_row(line, n) -> (숫자 목록 \| None, 사유)` | 문자열 한 줄 → 숫자 n개 **변환** |
| `validate_matrix(matrix, n) -> (bool, 사유)` | 완성된 2차원 배열을 **검사만** |
| `read_matrix(title, n) -> Matrix` | 두 함수를 엮어 n줄을 받는 반복 |
| `_prompt(message) -> str` | `input()` 래퍼. Ctrl+C / Ctrl+D를 안내 후 정상 종료로 처리 |

두 검증 함수가 나뉜 이유: 모드 1은 키보드 문자열을 **변환**해야 하고,
모드 2의 `data.json`은 이미 숫자로 파싱돼 있어 **검사만** 필요하다.
그래서 `validate_matrix`는 모드 1·2 양쪽에서 재사용된다.

`read_matrix`는 성공한 줄만 쌓는다. 실패하면 `continue`로 건너뛰므로 쌓인 개수가 그대로고,
"틀린 줄만 다시 묻기"가 별도 로직 없이 이 구조에서 나온다.

입력단에서 막는 값이 두 가지 있다.

- **`nan` / `inf`** — `float('nan')`은 파싱에 성공하지만, nan은 어떤 비교에도 `False`를 돌려준다.
  그대로 두면 `is_tie`도 `>`도 False가 되어 근거 없이 `X`로 판정된다. 오류 없이 결과만 틀린다.
- **`True` / `False`** — `isinstance(True, int)`가 참이라 bool이 1.0/0.0으로 조용히 계산된다.

### 3.3 데이터 로드와 케이스 판정

| 함수 | 설명 |
|---|---|
| `load_data(path) -> (dict \| None, 사유)` | 파일 없음·JSON 오류를 **예외가 아닌 반환값**으로 |
| `extract_size(key) -> int \| None` | `'size_13_2'` → `13`. 형식이 다르면 `None` |
| `build_filters(raw) -> (필터 dict, 안내 문구 목록)` | 키를 표준 라벨로 바꿔 담고 결과를 보고 |
| `run_case(case_id, case, filters) -> dict` | 케이스 하나 판정. **어떤 경우에도 예외를 던지지 않는다** |
| `run_cases(patterns, filters) -> list` | 케이스 루프 + 예외 안전망 |

`run_case`는 **크기 3자 대조**(필터 존재 / 필터가 N×N / 패턴이 N×N)를 통과한 뒤에만 `mac()`을 부른다.
크기가 어긋난 채 부르면 `IndexError`로 프로그램이 죽어서 "모드 2는 중단되지 않는다"는 요구와 충돌한다.

`extract_size`는 `split('_')[1]`을 그대로 믿지 않는다. `parts[0] == 'size'`와 `isdigit()`까지 확인한다.
`filter5` 같은 키가 들어오면 `IndexError` 대신 `None`을 돌려준다.

### 3.4 성능 측정

| 함수 | 설명 |
|---|---|
| `measure_mac_ms(pattern, filter_matrix, repeat) -> float` | `repeat`회 반복 후 1회당 평균 ms |
| `collect_perf_inputs(n, filters, patterns)` | 측정에 쓸 행렬을 **측정 구간 밖에서** 고름 |
| `build_perf_rows(filters, patterns)` | 크기별 측정 결과 표 행 생성 |

반복 루프를 함수 **안**에 둔 것이 중요하다. 밖에 두면 호출부가 루프 중간에 `print`를 끼워넣기 쉽고,
그러면 출력 시간이 측정에 섞인다. `time.time()`이 아니라 `time.perf_counter()`를 쓴다(해상도).

### 3.5 패턴 생성기 (보너스이자 필수 의존)

| 함수 | 설명 |
|---|---|
| `generate_cross(n) -> Matrix` | 가운데 행·열이 1.0 |
| `generate_x(n) -> Matrix` | 두 대각선이 1.0 |
| `_empty_matrix(n) -> Matrix` | 0.0으로 채운 n×n |

보너스 과제지만 **필수 경로에 걸린다.** 성능 분석은 3×3을 포함해야 하는데
`data.json`에는 5×5·13×13·25×25 필터밖에 없다. 3×3은 생성기로 만들어 측정하고, 표 아래 각주로 밝힌다.

`_empty_matrix`를 따로 뺀 이유는 파이썬의 함정 때문이다.

```python
matrix = [[0.0] * n] * n    # 같은 행 객체를 n번 참조 → 한 칸만 바꿔도 모든 행이 바뀐다
matrix.append([0.0] * n)    # 행마다 새 리스트 → 안전
```

두 생성기 모두 1.0의 개수가 `2N-1`개다. 가로 N개 + 세로 N개인데 정중앙에서 한 번 겹치기 때문이다.

| case_id | Cross 점수 | X 점수 | \|차이\| | 판정 | expected | 결과 |
|---|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | 1.1e-16 | UNDECIDED | X | **FAIL** |
| size_5_2 | 8.9 | 0.1 | 8.8 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | 14.4 | X | X | PASS |

| size_25_2 | 52.9 | 0.1 | 52.8 | Cross | Cross | PASS |

### 4.2 FAIL 원인 분석 — 세 범주로 분리

실패 원인은 **데이터/스키마 문제 / 로직 문제 / 수치 비교 문제**로 나눠 진단해야 한다.
이번 결과의 FAIL 3건은 **전부 세 번째 범주**이며, 앞의 두 범주는 0건이다.

**(1) 데이터/스키마 문제 — 0건**

배포된 `data.json`은 스키마가 온전하다. `filters`에 `size_5`/`size_13`/`size_25`가 모두 있고
각각 `cross`/`x` 두 장을 가지며, 패턴 6개 모두 키 형식(`size_{N}_{idx}`)과 크기가 맞는다.

다만 이 범주의 실패가 발생하지 **않았을 뿐**, 발생하면 케이스 단위로 흡수하도록 구현했다.
필터 누락·패턴 크기 불일치·`input` 키 누락·삐뚤한 배열·`expected` 오염 등 손상 데이터로 검증한 결과,
프로그램은 중단되지 않고 해당 케이스만 사유와 함께 FAIL로 남긴 뒤 다음 케이스로 진행한다.
JSON 문법 자체가 깨진 경우만 예외로, 케이스 단위 처리가 의미 없으므로 모드 2를 중단하고 메뉴로 돌아간다.

**(2) 로직 문제 — 0건**

라벨 표기 혼선으로 인한 오판정이 원천 차단됐다. `expected`의 `'+'`와 필터 키의 `'cross'`를
데이터가 들어오는 경계에서 `Cross`로 정규화하고, 그 이후 코드에는 소문자 키가 존재하지 않는다.
정규화를 각 비교 지점마다 했다면 한 곳만 빠뜨려도 조용히 오판정이 났을 것이다.

`UNDECIDED`를 FAIL로 처리하는 것도 로직이 아니라 **정책**이다. 판정을 못 한 것이므로
`expected`가 무엇이든 정답과 일치할 수 없다. 이것을 PASS로 처리하면 "모르겠다"가 정답이 되어 버린다.

**(3) 수치 비교 문제 — 3건 (실제 원인)**

FAIL 3건은 모두 두 점수의 차이가 1e-15~1e-16 수준, 즉 부동소수점 오차 범위 안에서 만난 경우다.

데이터를 뜯어보면 이것이 **의도적으로 설계된 동점**임이 드러난다.
패턴 6개는 전부 순수 0/1의 교과서적 Cross·X 모양이고, `generate_cross(n)`/`generate_x(n)`의
출력과 값까지 완전히 일치한다. 즉 입력 쪽에는 함정이 없다.

함정은 **필터의 가중치**에 있다. 필터도 모양은 정상이지만 값이 1.0이 아니다.

| 필터 | 사용된 값 |
|---|---|
| size_5 cross | `0.0, 0.9, 1.0` — 가운데 칸만 0.9 |
| size_5 x | `0.0, 0.1` |
| size_13 x | `0.0, 0.3, 7.5` |
| size_25 cross | `0.0, 1.0, 4.9` |

`size_5_1`을 보자. 입력은 X 패턴이다. X 필터와는 9칸이 겹치는데 값이 전부 0.1이라
`0.1 × 9 = 0.8999999999999999`가 된다. Cross 필터와는 가운데 한 칸만 겹치는데 그 값이 0.9라 정확히 `0.9`다.
수학적으로는 같은 값이지만 부동소수점으로는 1.1e-16만큼 다르다.

**여기서 정책의 의미가 갈린다.** epsilon 없이 `>`로만 비교했다면 `size_5_1`은 `Cross`로 판정된다.
expected는 `X`이므로 여전히 FAIL이지만, 이번엔 **"우연히 오차 방향이 그래서" 나온 판정**이다.
`size_13_2`는 반대로 오차 덕분에 `X`가 되어 expected `Cross`와 어긋난다.
어느 쪽이든 근거가 없다. epsilon 정책은 **틀린 답을 맞게 바꾸는 장치가 아니라,
근거 없는 판정을 "판정 불가"라고 정직하게 말하게 하는 장치**다.

따라서 이 FAIL 3건은 버그가 아니라 **정책이 의도대로 작동한 결과**다.
고치려면 정책을 끄는 수밖에 없는데, 그러면 판정은 나오되 그 판정에 근거가 없다.

### 4.3 성능 분석과 O(N²) 근거

```
크기(N×N)     평균 시간(ms)   연산 횟수(N²)
--------------------------------------------
3×3                    0.001             9
5×5                    0.002            25
13×13                  0.010           169
25×25                  0.035           625

* 3×3 크기는 data.json에 데이터가 없어 생성기로 만든 패턴으로 측정했습니다.
```

측정 환경: Python 3.10.8 / macOS (Darwin 25.5.0) / arm64.
크기별로 MAC 연산을 10회 반복해 평균을 냈으며, 측정 구간에는 `mac()` 호출만 들어간다
(입력·출력·파일 읽기·행렬 생성 모두 제외). 반복 실행 시 13×13은 0.010~0.011, 25×25는 0.035~0.040으로 흔들린다.

**단순 배율 비교로는 O(N²)를 논증할 수 없다.** 실측하면 시간 배율이 N² 배율보다 항상 작게 나온다.

| 비교 | N² 배율 | 시간 배율 | 차이 |
|---|---|---|---|
| 3→5 | 2.78 | 2.17 | −22% |
| 5→13 | 6.76 | 5.52 | −18% |
| 13→25 | 3.70 | 3.35 | −10% |

"연산이 69배니 시간도 69배"라고 쓰면 실측과 어긋난다(실제로는 약 35배).
원인은 **호출 1회당 고정 오버헤드**다. 함수 호출과 루프 준비 비용은 크기와 무관하게 붙는데,
3×3은 곱셈이 9번뿐이라 이 고정비가 전체에서 차지하는 비중이 크다.
그래서 작은 크기의 시간이 상대적으로 부풀려지고, 배율을 그대로 비교하면 왜곡된다.

측정값을 `시간 = a + b·N²` 모델에 맞추면 구조가 드러난다(노이즈 제거를 위해 30세트 중앙값 사용).

- `a`(고정 오버헤드) ≈ 0.00065 ms
- `b`(연산 1회당 비용) ≈ **0.057 µs — 크기와 무관하게 일정**
- 모델 예측 오차: N=5 −5.9% / N=13 +5.0% / N=25 −0.4%

| 크기 | 연산 횟수 | 연산 1회당 |
|---|---|---|
| 3×3 | 9 | 0.100 µs |
| 5×5 | 25 | 0.078 µs |
| 13×13 | 169 | 0.064 µs |
| 25×25 | 625 | 0.058 µs |

**연산 1회당 비용이 일정하게 수렴한다는 것이 O(N²)의 직접적 근거다.**
전체 시간은 연산 횟수 N²에 비례하고, 크기가 커질수록 고정비 비중이 줄어 배율도 N²에 수렴한다.
실제로 배율 차이가 3→5의 −22%에서 13→25의 −10%로 좁혀진다.

패턴 크기가 2배가 되면 연산은 4배가 된다. 25×25는 3×3의 약 69배(625/9)를 계산한다.
실제 AI 모델은 수백×수백 필터를 수천 개 쓰므로 이 증가가 감당 불가능해지고,
그래서 MAC 연산을 병렬로 처리하는 전용 칩(NPU)이 필요해진다.

## 5. 보너스 과제

### 5.1 1차원 배열 최적화 (메뉴 `3`)

2차원 배열을 길이 N²의 1차원 배열로 펴서 접근 단계를 줄였다. 기존 `mac()`은 비교 대상으로 그대로 두었다.

```
크기(N×N)   2차원(ms)    1차원(ms)    변화       연산 횟수(N²)
---------------------------------------------------------------
3×3              0.0010       0.0005     -43.5%             9
5×5              0.0020       0.0012     -40.0%            25
13×13            0.0109       0.0070     -35.1%           169
25×25            0.0357       0.0258     -27.8%           625

두 방식의 MAC 점수는 모든 크기에서 동일합니다 (|차이| < 1e-09).
```

1차원이 27~44% 빠르다. 크기가 작을수록 이득이 큰데, 2차원은 **행마다 안쪽 루프를 새로 세우는**
비용이 붙기 때문이다. N이 커지면 원소당 계산이 지배적이 되어 격차가 줄어든다.

**다만 변환 비용까지 포함하면 결론이 뒤집힌다.** `flatten` 자체가 계산의 0.6~0.8배를 쓴다.

| 크기 | 2차원/회 | 1차원/회 | 변환(2장) | 손익분기 |
|---|---|---|---|---|
| 3×3 | 0.0010 | 0.0005 | 0.0008 | 1.9회 |
| 5×5 | 0.0020 | 0.0011 | 0.0017 | 2.1회 |
| 13×13 | 0.0108 | 0.0069 | 0.0103 | 2.6회 |
| 25×25 | 0.0358 | 0.0258 | 0.0339 | 3.4회 |

매번 변환한다면 오히려 느리다: 3×3 +56% / 5×5 +53% / 13×13 +66% / 25×25 +71%.

즉 1차원화는 **"펴 둔 상태로 여러 번 재사용할 때"만** 최적화다.
이 과제는 `REPEAT=10`이라 손익분기(최대 3.4회)를 넘겨 이득이 난다.
실제 NPU가 데이터를 처음부터 1차원으로 눕혀 두는 이유도 같다. 변환을 매번 하지 않기 위해서다.

### 5.2 패턴 생성기

`generate_cross(n)`과 `generate_x(n)`으로 임의 크기의 Cross·X 패턴을 만든다.
성능 분석의 3×3 측정에 재사용되며(§3.5), `data.json`의 패턴 6개를 값까지 정확히 재현한다.
